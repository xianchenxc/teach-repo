自定义 Tool、错误与安全钩子

本课成果：你会写一个会「抛错」的自定义工具，让 Runtime 把错误回填给模型，再用 beforeToolCall / afterToolCall 两道钩子做执行前拦截与执行后审计。

已用 PI 0.84.3 真实运行
先预测

工具 execute 里如果出错了，正确做法是返回一个内容为「错误信息」的文本，还是直接 throw？拦截一个危险命令，应该在工具执行之前还是之后？先写下答案。

1. 工具失败的正确姿势：throw，不要编进 content

这是 AgentTool 契约里最反直觉、也最重要的一条。源码注释（types.ts）原话：

Execute the tool call. Throw on failure instead of encoding errors in content.

为什么？因为 content 是模型能读到的「正常结果」。你把错误塞进去，模型分不清这是成功输出还是失败提示。而 throw 会被 Runtime 捕获，转成一个带 isError: true 标记的结果，语义明确。

const divideTool: AgentTool<typeof divideParameters> = {
  name: "divide",
  label: "Divide",
  description: "Divide a by b. Throws if b is zero.",
  parameters: Type.Object({ a: Type.Number(), b: Type.Number() }),
  execute: async (_id, { a, b }) => {
    if (b === 0) throw new Error("Division by zero");   // 错误路径：throw
    return {
      content: [{ type: "text", text: String(a / b) }],   // 正常路径：content
      details: { a, b, quotient: a / b },
    };
  },
};

2. 错误如何回到模型：源码里的捕获点

在 agent-loop.ts 的 executePreparedToolCall 里，execute 被包在 try/catch 中：

  1. prepared.tool.execute(...) 抛出异常。
  2. catch 分支调用 createErrorToolResult(error.message)，生成 { content: [{type:"text", text: message}], details: {} }。
  3. 结果被标为 isError: true，最终写进一条 role:"toolResult" 消息。
  4. 下一轮模型调用能看到这条错误消息，从而「看到错误、换个参数重试」。
不止 execute 会触发错误结果，以下情形都会产生 isError: true 的 toolResult：工具不存在（Tool X not found）、参数校验失败、beforeToolCall 拦截、afterToolCall 自身抛错。它们共用同一条「错误 toolResult」通道。

3. 安全钩子一：beforeToolCall 拦截执行

在参数校验之后、execute 运行之前调用。返回 { block: true, reason } 即阻止执行，Runtime 会生成一条错误 toolResult，execute 根本不会运行。

const agent = new Agent({
  initialState: { systemPrompt: "...", model, tools: [divideTool, shellTool] },
  streamFn: models.streamSimple.bind(models),

  beforeToolCall: async ({ toolCall, args }) => {
    if (toolCall.name === "shell") {
      const command = args.command;
      if (!ALLOWLIST.has(command)) {
        return { block: true, reason: `Command "${command}" is not in the allowlist` };
      }
    }
    return undefined;  // 不拦截
  },
});

4. 安全钩子二：afterToolCall 审计 / 改写

在 execute 结束之后、结果最终写入前调用。返回的字段会整字段替换（content、details 不做深合并），缺省字段保留原值。

afterToolCall: async ({ toolCall, result, isError }) => {
  if (!isError) {
    // 执行后审计：整体重写 content 和 details
    return {
      content: [...result.content, { type: "text", text: " [audited]" }],
      details: { ...result.details, audited: true },
    };
  }
  return undefined;
},
关键边界：afterToolCall 只对真正执行过的工具触发（包括 execute 抛错的），对 beforeToolCall 拦截掉的工具不会触发——拦截发生在更早的 prepare 阶段，直接走「立即出错」分支。

5. 完整实验：一次运行看三个机制

脚本让模型依次：成功除法 → 除零抛错 → 换参数重试 → 执行被拦截的 shell 命令 → 收尾回答。五轮模型调用，确定性、零 API 成本。

本机真实输出
[afterToolCall] divide isError=false
[tool_result] divide isError=false
[afterToolCall] divide isError=true
[tool_result] divide isError=true
[afterToolCall] divide isError=false
[tool_result] divide isError=false
[tool_result] shell isError=true
Done: recovered from divide-by-zero and a blocked shell command.

[roles] user -> assistant -> toolResult -> assistant -> toolResult -> assistant -> toolResult -> assistant -> toolResult -> assistant
[provider calls] 5
[errors] ["Division by zero","Command \"rm -rf /\" is not in the allowlist"]
[audited] 2
[verify] all assertions passed

从输出读出三件事：

  • 错误被回填：isError=true 出现在两次 toolResult 上，且 [errors] 里能读到抛错文案与拦截理由。
  • 拦截未执行：shell isError=true 前面没有 [afterToolCall] shell ...，证明被拦截的工具根本没进 execute。
  • 审计生效：两次成功除法都经过 afterToolCall，[audited] 2 说明改写已落到结果上。
