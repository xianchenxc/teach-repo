先预测

如果要把一个 Agent 的对话「关掉再打开」，你需要保存什么？是保存 systemPrompt，还是保存消息列表 messages，还是保存工具定义？先写下答案，再看下文。

1. AgentState：Agent 到底拥有哪些状态

前几课我们一直在 initialState 里传 systemPrompt / model / tools，运行后又读 agent.state.messages。这一节把它们一次说清。types.ts 里的 AgentState 长这样：

interface AgentState {
  systemPrompt: string;          // 每次请求都携带的系统提示
  model: Model<any>;              // 后续 turn 使用的模型
  thinkingLevel: ThinkingLevel;   // 推理级别（off / low / medium / high ...）
  set tools(tools); get tools();  // 赋值新数组 → 拷贝顶层数组
  set messages(msgs); get messages(); // 同上，会话转录
  readonly isStreaming: boolean;      // 是否正在处理 prompt/continuation
  readonly streamingMessage?;         // 当前流式回答的部分消息
  readonly pendingToolCalls;          // 正在执行的 tool call id 集合
  readonly errorMessage?;             // 最近一次失败/中止的 turn 错误
}

关键边界：tools 和 messages 是 accessor 属性——你给它们赋新数组时，Agent 会先拷贝顶层数组再存。所以外部改原数组不会悄悄污染 Agent 的内部状态。而 isStreaming / streamingMessage / pendingToolCalls / errorMessage 是运行时字段，只读、由 loop 维护，不属于「持久化」的范畴。

2. 事件流：一次 run 的完整生命周期

agent.subscribe(listener) 订阅的 AgentEvent 是一个联合类型，覆盖三类事件——agent 生命周期、turn 生命周期、消息生命周期、工具执行生命周期。本实验真实观测到的顺序（去重后）是：

[event types] agent_start -> turn_start -> message_start -> message_end
           -> message_update -> tool_execution_start -> tool_execution_end
           -> turn_end -> agent_end

逐条读：

  • agent_start / agent_end —— 一次 run 的起止。注意 agent_end 是 run 发出的最后一个事件，但 awaited 的 agent_end listener 全部 settle 之后，Agent 才算真正 idle。
  • turn_start / turn_end —— 一个 turn = 一次 assistant 回答 + 它触发的全部工具调用与结果。本实验 session 1 有两个 turn（调用工具 + 收尾回答）。
  • message_start / message_update / message_end —— 消息生命周期。message_update 只在 assistant 流式输出时触发，一次回答会触发多次（每个 text delta 一次）。
  • tool_execution_start / tool_execution_update / tool_execution_end —— 工具执行生命周期。

3. 持久化：快照 → 恢复 → 续跑

PI 的核心 Agent 本身不做磁盘落盘——它把「会话」完整地暴露在 agent.state.messages 里（一条条 user / assistant / toolResult 消息，全 JSON 可序列化，timestamp 是数字）。持久化的本质就是：序列化这条转录，下次用 initialState.messages 交还给一个新 Agent。

// 会话 1 结束后，落盘快照
const snapshot = JSON.stringify({
  systemPrompt: agentA.state.systemPrompt,
  modelId: agentA.state.model.id,
  messages: agentA.state.messages,   // 转录本体
});

// 新进程里，恢复并接着聊
const restored = JSON.parse(snapshot);
const agentB = new Agent({
  initialState: {
    systemPrompt: restored.systemPrompt,
    model: faux.getModel(),
    tools: [rememberTool],
    messages: restored.messages,     // ← 续跑的关键
  },
  streamFn: models.streamSimple.bind(models),
});

要点：toolResult 消息和普通消息一样会被持久化——所以恢复后，模型仍然「记得」之前调用过什么工具、得到了什么结果。想清空会话则调 agent.reset()（会清空 messages 与运行时状态，且正在处理时会抛错拒绝）。

4. 上下文窗口管理：transformContext

持久化的转录会越攒越长，迟早顶到模型的上下文窗口。AgentLoopConfig 里有两个专门钩子：

  • transformContext(messages) —— 在 convertToLlm 之前、针对 AgentMessage[] 做裁剪/注入（比如截掉最旧的几轮、拼接外部资料）。
  • convertToLlm(messages) —— 把 AgentMessage[] 转成 LLM 能懂的 Message[]，默认过滤掉非 user/assistant/toolResult 的自定义消息。

两者契约一致：不 throw、不 reject，返回原数组或安全回退值。

5. 官方 session-backends（概览）

生产级持久化不必手写快照。PI 提供 @earendil-works/pi-session-backend-sqlite-node，用 node:sqlite 做适配器，提供 SQLite 会话仓库、迁移、物化视图和可选的 FTS 全文搜索：

await using repository = new SqliteSessionRepository(options);
const search = createSqliteSessionSearch(options);
const session = await repository.create({ cwd });
await session.appendMessage(message);

for await (const hit of search.search("needle")) { /* ... */ }

本课实验只用手写快照（零依赖、零 API 成本、足够讲清机制）；生产项目再引入官方 backend。Agent 构造函数还接受 sessionId，会转发给 provider 用于缓存感知的 backend。

6. 完整实验：一次运行看状态、事件与持久化

脚本跑两个「会话」：会话 1 让模型调用 remember 工具存一条事实并确认；然后序列化转录、恢复进一个新 Agent；会话 2 追问「我之前说过什么」，模型基于恢复的转录答出那条事实。零 API 成本、确定性输出。

本机真实输出 
[session-1 roles] user -> assistant -> toolResult -> assistant
[snapshot] 4 messages, <N> bytes
[restored roles] user -> assistant -> toolResult -> assistant
[session-2 roles] user -> assistant -> toolResult -> assistant -> user -> assistant
[event types] agent_start -> turn_start -> message_start -> message_end -> message_update -> tool_execution_start -> tool_execution_end -> turn_end -> agent_end
[provider calls] 3
[verify] all assertions passed

从输出读出三件事：

  • 状态可序列化：会话 1 的 4 条消息（含 toolResult）被 JSON 快照，恢复后 [restored roles] 与之一致。
  • 转录可续跑：会话 2 在 4 条恢复消息后追加新的 user/assistant，得到 6 段序列，且模型答出了持久化的事实。
  • 事件覆盖完整生命周期：一次带工具的 run 从 agent_start 走到 agent_end，中间经过消息、工具、turn 三类事件。
