三层架构与 Agent Loop

本课的可见成果：你能把 PI 的三个核心包放到正确层级，并沿源码追踪一次工具调用闭环。

先预测，再阅读

如果模型已经返回一个 toolCall，谁应该负责校验参数、执行工具并把 toolResult 再交给模型？先在脑中选：Provider 层、Agent Runtime 层，还是 Coding Harness 层。

1. PI 不是一个“大 Agent 类”

@earendil-works/pi-ai统一 Provider / Model / 流式 LLM API；定义模型能看到的消息和工具 schema。
@earendil-works/pi-agent-core维护 Agent 状态，运行循环，校验并执行工具，发出事件。
@earendil-works/pi-coding-agent组装编码产品：内置工具、会话、扩展、skills、上下文文件与 CLI。
底层能力 → 通用运行时 → 具体产品

关键边界：pi-ai 会告诉你模型“想调用什么”，但不会替应用执行工具；pi-agent-core 才拥有工具执行闭环；pi-coding-agent 再把这个闭环产品化成编码 Agent。

来源：仓库 README、agent-core README。

2. 一次工具调用的真实源码路径

  1. agent.prompt() 把用户消息加入 Agent 上下文，开始一个 run。
  2. runLoop() 进入 turn，并调用 streamAssistantResponse()。
  3. 发送给模型前：transformContext() 可裁剪/压缩 Agent 消息；convertToLlm() 再转为 LLM 能理解的消息。
  4. 模型流产出 assistant message；如果内容包含 toolCall，循环不会结束。
  5. executeToolCalls() 选择并行或串行执行；工具自己的 executionMode: "sequential" 可强制整批串行。
  6. prepareToolCall() 查找工具、准备并校验参数，再运行 beforeToolCall 安全钩子。
  7. 工具 execute() 返回结果或抛错；随后 afterToolCall 可审计/改写结果。
  8. 结果被标准化为 toolResult 消息，加入上下文；下一 turn 再请求模型生成最终回答。
把循环压成一句话：
User → LLM → Assistant(toolCall) → Runtime executes → ToolResult → LLM → Assistant(text)

3. 两个容易混淆的机制

AgentMessage 与 LLM Message

AgentMessage 可以包含应用自定义消息；模型只理解 user、assistant、toolResult。因此 PI 把“应用历史”与“模型上下文”分开，并在每轮模型调用边界执行转换。

事件流与持久状态

事件（如 message_update、tool_execution_start）服务 UI、日志和观察者；消息数组是 Agent 的对话状态。看到事件不等于状态已经持久化，持久化由上层会话实现负责。
